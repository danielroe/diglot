---
title: Astro
description: Add translated Markdown and MDX pages to an Astro content collection, built from the records of a translations repository.
---

`@diglot/astro` brings diglot translations into an [Astro](https://astro.build) site. You add its integration to your Astro config and use its loader for a collection in place of Astro's `glob()` loader. Next to your source pages, the loader then adds translated entries for the locales of your `i18n` config. The translations come straight from the records of a translations repository, so your site never holds translated copies of its pages.

::package-info{name="@diglot/astro" directory="packages/astro"}
::

::note
Building with Starlight? Use [`@diglot/starlight`](/integrations/starlight), which sets up this integration for Starlight's locales, docs collection and components.
::

The package needs Astro 7 and Node.js 22.23.4 or later. It translates Markdown pages, and MDX pages once you also use [`@astrojs/mdx`](https://docs.astro.build/en/guides/integrations-guide/mdx/).

## Prepare the translations repository

Your site needs the translations repository on disk, for example as a git submodule or as a checkout that your build pulls in. The translated pages are built straight from its records, so you don't need to run `diglot build` for your site.

In that repository, set `parser` to `satteri`:

```ts [translations/diglot.config.ts]
import { defineConfig } from '@diglot/core'

export default defineConfig({
  locales: ['fr', 'pt-BR'],
  parser: 'satteri',
})
```

`satteri` reads Markdown the way Astro does, whether your site renders with Sätteri, Astro's default, or with unified. The `comark` and `mdast` parsers read MDC, a component syntax that Astro doesn't support, so they would treat text such as a `::card` block or `{target="_blank"}` after a link differently from the way your site shows it. If your configuration uses one of them, Astro shows a warning when it loads your collection. Your pages are matched to the records with this configuration and its [policy](/guide/concepts/segments), so extract again whenever you change either of them.

## Add the integration

In your Astro config, add `diglot()` with `translations`, the directory of the translations repository relative to the project root. If your collection holds MDX pages, add `mdx()` as well:

```js [astro.config.mjs]
import mdx from '@astrojs/mdx'
import diglot from '@diglot/astro'
import { defineConfig } from 'astro/config'

export default defineConfig({
  integrations: [mdx(), diglot({ translations: './translations' })],
  i18n: {
    defaultLocale: 'en',
    locales: ['en', 'fr', { path: 'pt-br', codes: ['pt-BR'] }],
  },
})
```

The locales come from your `i18n` option, which the integration requires, so you don't list them a second time. Another integration can set `i18n` too, as Starlight does. Your default locale holds the source pages, and every other locale is translated when `diglot.config.ts` lists it too, by its path or by one of its codes. Case doesn't matter, so `pt-br` in Astro and `pt-BR` in diglot are the same locale. A locale that diglot doesn't list only has the pages you write for it yourself.

## Load a collection

In `src/content.config.ts`, use `diglotLoader()` where you would use `glob()`. It accepts the same `pattern`, `base` and `generateId` options:

```ts [src/content.config.ts]
import { diglotLoader } from '@diglot/astro'
import { z } from 'astro/zod'
import { defineCollection } from 'astro:content'

const docs = defineCollection({
  loader: diglotLoader({
    pattern: '**/*.{md,mdx}',
    base: './src/content/docs',
  }),
  schema: z.object({
    title: z.string(),
    description: z.string().optional(),
  }),
})

export const collections = { docs }
```

The loader only works together with the integration, so keep `diglot()` in your Astro config.

## Add data to translated entries

`diglotLoader()` also takes a `data` function, which returns fields to add to each translated entry. It receives the entry's `id`, its `locale` and `localePath`, the `source` file of the page, its translated `frontmatter`, and `updatedAt`, the date of the newest translation that the page uses. `updatedAt` is `undefined` when none of those records has a date that JavaScript can parse. The fields it returns replace frontmatter fields of the same name, and they are validated against your collection schema like the rest of the entry. With a `translatedAt` field in your schema, the following loader dates every translated page by its translations:

```ts [src/content.config.ts]
diglotLoader({
  pattern: '**/*.{md,mdx}',
  base: './src/content/docs',
  data: ({ updatedAt }) => ({ translatedAt: updatedAt }),
})
```

## Entry ids

Your source pages can live in a directory for the default locale or at the root of the collection. Either way, a translated entry takes the id of its source entry, with the locale path in front:

| Source file | Source id | Id in `fr` |
| --- | --- | --- |
| `en/guide.md` | `en/guide` | `fr/guide` |
| `en/index.md` | `en` | `fr` |
| `guide.md` | `guide` | `fr/guide` |
| `index.md` | `index` | `fr` |

These are the ids that Astro would give `fr/guide.md` and `fr/index.md`, so the locale segment is always lower case: a page in `pt-BR` has the id `pt-br/guide`. When your source pages live in a directory for the default locale, a route such as `src/pages/[...slug].astro` that builds its paths from `entry.id` serves every locale. When they live at the root, map the `index` id to an empty slug in that route, or your home page is served at `/index/`. When you pass `generateId`, it sets the ids of the source entries, and the translated ids follow from them in the same way.

## What a translated entry contains

A translated page is your source page with the locale's translations in place. Text without a usable translation stays in the source language, so a partly translated page is still complete, and rejected translations never appear. The frontmatter fields that the policy marks as prose, `title` and `description` among them, are translated too, and they have to match your collection schema just like the source.

Translated pages use your Markdown configuration, and relative image paths work the same way as in the source. URLs are never translated, so a link to `/en/guide/` points to the same address on the French page.

A locale only gets an entry for a page when at least one translation applies to it. Until someone translates a page, it stays out of that locale.

## MDX pages

An MDX page is translated like any other: the text, the string props that the policy lists for a component, and the frontmatter. Imports, exports, expressions and inline JSX stay exactly as they are in the source. Components, relative imports and images work the same way as in the source, and your MDX configuration applies to the translations too. See [MDX](/adapters/mdast#mdx) for what counts as translatable.

## Pages you translate by hand

When you write a page for a locale yourself, for example a `fr/about.md` that your `pattern` matches, your page is used and diglot doesn't add a translation of its own. You can therefore write some pages by hand and let diglot translate the rest of the locale. Pages in a locale that `diglot.config.ts` doesn't list are never treated as source pages, so they aren't translated into the other locales.

## Development

During `astro dev`, a change to a record, to `diglot.config.ts` or to a source page shows up in the translated pages without a restart.

## Limitations

Translations are added to content collections, so Markdown pages in `src/pages` aren't translated. Pages with TOML frontmatter (`+++`) aren't translated either, because diglot only translates YAML frontmatter.
