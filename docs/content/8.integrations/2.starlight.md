`@diglot/starlight` brings diglot translations into a [Starlight](https://starlight.astro.build) site. It builds on the [Astro integration](/integrations/astro) and sets it up the way Starlight works. Your locales come from the Starlight config, and the docs collection loads the same files as Starlight's own loader. The components and frontmatter fields that Starlight shows are translated as well.

::package-info{name="@diglot/starlight" directory="packages/starlight"}
::

The package needs Starlight 0.42, Astro 7 and Node.js 22.23.4 or later.

## Prepare the translations repository

In the `diglot.config.ts` of your translations repository, use `starlightPolicy` and the `satteri` parser:

```ts [translations/diglot.config.ts]
import { defineConfig, starlightPolicy } from '@diglot/core'

export default defineConfig({
  locales: ['fr', 'zh-CN'],
  parser: 'satteri',
  policy: starlightPolicy,
})
```

The policy marks the parts of a Starlight page that are prose. It covers the titles of asides, cards and link cards, the descriptions of link cards, the labels of tabs and icons, and the text of badges. It also covers the frontmatter fields that Starlight shows to readers, such as `sidebar.label`, `sidebar.badge`, `hero.tagline`, `banner.content` and the labels of `prev` and `next`. The HTML of `banner.content` is protected, so translators see its tags as placeholders and translate the text of its links. The file names in a `<FileTree>` aren't extracted. Like the rest of `@diglot/core`, the policy needs no installation in a translations repository, because the `diglot` command provides `@diglot/core` to its config.

The `satteri` parser reads Markdown the way Astro and Starlight do, including the `:::tip[Title]` syntax of asides. See [Astro](/integrations/astro#prepare-the-translations-repository) for why the parser matters.

## Add the plugin

Add `diglot()` to the `plugins` of your Starlight config, with `translations`, the directory of the translations repository relative to the project root:

```js [astro.config.mjs]
import starlight from '@astrojs/starlight'
import diglot from '@diglot/starlight'
import { defineConfig } from 'astro/config'

export default defineConfig({
  integrations: [
    starlight({
      title: 'My docs',
      locales: {
        'root': { label: 'English', lang: 'en' },
        'fr': { label: 'Français', lang: 'fr' },
        'zh-cn': { label: '简体中文', lang: 'zh-CN' },
      },
      plugins: [diglot({ translations: './translations' })],
    }),
  ],
})
```

Your Starlight `locales` are all the configuration diglot needs, so you don't add an `i18n` option to your Astro config. Every locale other than your default one is translated when `diglot.config.ts` lists it too, by its directory or its `lang`. Case doesn't matter. Without `locales`, there is nothing to translate into, and the plugin logs a warning when Starlight starts.

## Load the docs collection

In `src/content.config.ts`, use `diglotDocsLoader()` in place of Starlight's `docsLoader()`:

```ts [src/content.config.ts]
import { docsSchema } from '@astrojs/starlight/schema'
import { diglotDocsLoader } from '@diglot/starlight'
import { defineCollection } from 'astro:content'

export const collections = {
  docs: defineCollection({ loader: diglotDocsLoader(), schema: docsSchema() }),
}
```

It loads the same files as `docsLoader()` and accepts its `generateId` option, so your existing pages keep their ids and URLs. The translated pages appear next to them, in each locale's directory. Pages in `.md` and `.mdx` files are translated, while the other files that Starlight loads, such as `.markdown` or Markdoc pages, stay in their source language.

## What your readers see

A translated page uses the same layout as its source page. Its title, its sidebar label and the text of its components are translated. The autogenerated parts of your sidebar list the translated pages in the same order as the source pages. Labels that you set in the Starlight config, such as the label of a sidebar group, aren't part of any page. Translate them with Starlight's own `translations` option.

Text without a translation stays in the source language, so a partly translated page is still complete. Until someone translates a page, Starlight shows the source page in its place. A notice tells readers that the content isn't available in their language yet.

When your Starlight config sets `editLink.baseUrl`, the edit link of a translated page leads to its source page, because that is the file in your repository. With `lastUpdated`, a translated page shows the date of its newest translation. A page whose frontmatter sets `editUrl` to a URL or `false`, or `lastUpdated` to a date or `false`, keeps that value. The plugin reads `editLink` and `lastUpdated` when it is set up, so list it after any Starlight plugin that changes them.

Pages that you translate by hand work as usual. When a locale's directory already contains a page, diglot keeps it and doesn't add a translation of its own.
