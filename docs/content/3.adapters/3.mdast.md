`@diglot/mdast` is the remark and mdast adapter, for markdown parsed with `remark-parse`, `remark-gfm`, `remark-frontmatter` and `remark-mdc`. It suits Astro, Docusaurus, Starlight or plain markdown sources.

::package-info{name="@diglot/mdast" directory="packages/mdast" install="pnpm add @diglot/mdast @diglot/core"}
::

## Usage

```ts
import { apply, extract } from '@diglot/mdast'

const segments = await extract(markdown, { file: 'docs/intro.md' })

const { markdown: translated, report } = await apply(markdown, new Map([[segments[0].hash, 'Introduction']]))
```

## extract

`extract(source, { file, policy })` returns the same segments, with the same hashes, as `@diglot/comark` for the same document, with line positions that are exact for each node. Protected spans are sliced from the source.

## apply

`apply(source, translations, { policy })` validates each translation and splices it into the source, so everything outside the translated units is preserved byte for byte. Frontmatter and YAML props are rewritten as YAML scalars, inline props keep their attribute syntax, and code comments keep their indentation and comment syntax. A unit that can't be located in the source is reported as `unaddressable` and keeps its source text.

With `onSegment`, each segment produces an [`ApplySegmentEvent`](/core/apply). Attributes you set with `target.setAttribute(name, value)` on headings, paragraphs and table cells are returned as `annotations`, located in the applied markdown. Other segments have a `null` target. `annotate(tree, annotations)` sets them as `data.hProperties` on a tree parsed from the applied markdown, and renders the paragraphs of tight list items as `<span>` so that their attributes reach the HTML.

```ts
const { markdown: translated, annotations } = await apply(markdown, segment => records.get(segment.hash), {
  onSegment(event) {
    if (event.outcome === 'missing' || event.outcome === 'rejected')
      event.target?.setAttribute('lang', 'en')
  },
})
const tree = processor.parse(translated)
annotate(tree, annotations)
```

## parse

`parse(source, { parser })` exposes the pipeline the adapter uses.

## Parsers

`extract`, `apply` and `parse` take a `parser` option. `remark` is the default. `satteri` uses [Sätteri](https://satteri.bruits.org), a Markdown parser written in Rust, which is much faster. It is an optional peer dependency, so install it first:

```bash
pnpm add satteri
```

```ts
const segments = await extract(markdown, { parser: 'satteri' })
```

Sätteri reads directives the same way as remark-directive, which Starlight uses. `:::` blocks such as asides are translated like components with either parser, and with Sätteri their titles (`:::tip[Title]`) are translated too. Inline directives with a label or attributes, such as `:badge[New]`, are kept as placeholders. Sätteri has no MDC support, so block components such as `::card` are not parsed and their markers can end up in translated text. Keep `remark` for MDC sources. For other markdown, both parsers produce the same segments and hashes, so existing translations keep applying. One exception: Sätteri skips TOML frontmatter (`+++`), which remark reads as a paragraph. Pass the same `parser` to `extract` and `apply`.

## Heading anchors

The renderer generates heading anchors from the heading text, so translated headings get translated anchors unless your renderer supports explicit ids. Links from other pages to a heading therefore need the anchor of the translated heading, or an explicit id on the heading.
