---
title: Use translations in your site
description: Read a locale bundle and apply it to documents with an adapter when you render your site.
---

Records are the source of truth, but your site shouldn't read thousands of small files. `diglot build` collects the records of a locale into one bundle, and an adapter applies that bundle to a document when you render it.

## Build the bundles

```bash
pnpm dlx @diglot/cli build
```

This writes `dist/<locale>.json`, containing `{ version, locale, records }` with records keyed by hash. Only records that a source still uses are included, and the output reports how many were skipped as unused. Pass `--all` to include every record. The [Action](/workflow/action/overview) builds the same bundles at the end of a run.

## Apply a bundle

Parse the bundle with `parseBundle` from [`@diglot/store`](/store/records-and-bundles), which validates every record and returns a `Map` keyed by hash. Then give that map to the `apply` function of the adapter that matches your parser:

```ts
import { readFile } from 'node:fs/promises'
import { apply, parse, render } from '@diglot/comark'
import { parseBundle } from '@diglot/store'

const records = parseBundle(await readFile('dist/fr.json', 'utf8'))

const doc = await parse(markdown)
const { doc: translated, report } = await apply(doc, records)

const output = await render(translated)
```

`apply` extracts the document's segments, looks up each hash in the map, validates the translation against the current source and replaces the text. The report counts applied, missing and rejected segments. A segment without a usable translation keeps its source text, so a page is always complete, and the protected spans always come from the current source.

When your site consumes markdown strings, use `@diglot/mdast` instead, with `parser` set to `mdast` in your configuration, or to `satteri` for sources without MDC. Its `apply` takes the markdown string and returns markdown. Whichever adapter you use, apply the same parser and [policy](/guide/concepts/segments) that you configured for extraction, or the segments won't line up with the bundle.

`.mdx` files always need `@diglot/mdast`, whichever parser you configured. Pass the file path as `file`, or `format: 'mdx'`, so that `apply` reads them as MDX. When your configuration uses `parser: 'satteri'`, pass `parser: 'satteri'` to `apply` as well. The [policy snapshot](/core/policy-and-config#snapshots) doesn't record the parser, so a server that applies translations at runtime has to pass these options itself.

## Translate an Astro site

If your site is built with Astro, you don't apply bundles yourself. Add the [Astro integration](/integrations/astro), and your content collections get a translated page for every Markdown or MDX page that has translations in a locale, built straight from the records of your translations repository.

## Translate an Angular app

If your app is built with Angular, follow the [Angular recipe](/guide/how-to/translate-an-angular-app). It fetches the bundle of the current locale once, applies it to each Markdown document your components ask for, and hands the result from the server to the browser when you render on the server.

## Serve the latest translations

A bundle is fixed at build time. To serve translations as soon as they are committed, read the translations repository from an archive on your server with [`@diglot/store/runtime`](/store/runtime), and restore the policy snapshot so that your segments hash the same way. Navigation titles and title templates that you build at runtime can be translated one value at a time with [`translateLabel`](/adapters/comark#labels).

## Mark untranslated text

Readers benefit from knowing which text isn't translated. Both adapters accept an `onSegment` callback that receives each segment's outcome and a handle to set an attribute on its block:

```ts
const { doc: translated } = await apply(doc, records, {
  onSegment(event) {
    if (event.outcome === 'missing' || event.outcome === 'rejected')
      event.target?.setAttribute('lang', 'en')
  },
})
```

The `lang` attribute lets screen readers pronounce the fallback text correctly and lets your CSS style it. `event.status` also tells you whether a translation is `machine`, `pending-review`, `edited` or `verified`, so you can flag drafts. See [apply events](/core/apply).
